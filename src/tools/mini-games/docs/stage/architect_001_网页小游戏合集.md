# 架构方案：轻量网页小游戏合集（打发碎片化时间）

- 对应 innovator：innovator_001_网页小游戏合集.md
- 对应 pm：pm_001_网页小游戏合集.md（结论：可集成）
- 设计日期：2026-10-17

## 需求回顾与设计依据

- 需求：在方子内新增「小游戏」工具，内置多款轻量、难度适中的益智类网页游戏（2048、翻牌配对、华容道/拼图、消消乐、数独等），纯前端、离线可玩、本地保存进度，并可持续扩充游戏库。
- PM 结论：**可集成（新增）**。技术可行（纯前端 Canvas）、零核心改动（方子工具框架）、无合规与成本风险，作为留存/活跃增强功能，Freemium 变现。
- 设计前提：无自研后端、纯前端 PWA、EdgeOne Pages 静态托管（25MiB 资源上限）、零资金投入、复用 fangzi 现有工具框架与计费能力。

## 技术方案

### 系统架构

```
fangzi PWA（Vue3 + Vite + TS，EdgeOne Pages 静态托管）
 └─ src/tools/games/（新工具目录，走现有工具框架：manifest + 组件）
     ├─ GameShell.vue        # 游戏外壳：游戏列表/计分/计时/重开/暂停/难度
     ├─ games/               # 单款游戏组件（Canvas 渲染，互相独立）
     │   ├─ game-2048.vue
     │   ├─ game-memory.vue  # 翻牌配对
     │   ├─ game-klotski.vue # 华容道
     │   ├─ game-merge.vue   # 数字消消乐（合并类）
     │   └─ game-sudoku.vue
     ├─ engine/              # 共用游戏逻辑（游戏循环、分数、本地存档）
     │   ├─ loop.ts          # requestAnimationFrame 循环封装
     │   ├─ storage.ts       # IndexedDB 最高分/进度（复用方子本地存储约定）
     │   └─ types.ts
     └─ manifest.json        # 工具注册（名称/简介/关键词/计费）
```

- 搜索与路由：复用 fangzi 工具框架自动生成的检索与路由，零手工路由改动。
- 离线：新增资源经 vite-plugin-pwa 构建自动纳入 Service Worker 预缓存；单款游戏资源控制在 200KB 以内，整包远低于 25MiB 上限。

### 模块设计

| 模块 | 职责 | 数据流 |
|---|---|---|
| GameShell | 游戏列表页 + 统一外壳（分数/计时/重开/暂停/难度选择/最高分展示） | 读取 IndexedDB 进度 → 展示；启动/结束游戏 → 写回 |
| games/* | 各游戏 Canvas 渲染与交互逻辑 | 接收 GameShell 的难度/重开指令 → 输出分数/结束事件 |
| engine/loop | 帧循环、输入、状态机统一封装 | 游戏组件注册更新/绘制回调 |
| engine/storage | IndexedDB 读写（最高分、进度、已解锁） | 与 GameShell 双向 |

### 关键技术路线

- 渲染：原生 Canvas 2D + requestAnimationFrame（程序化绘制，无图片素材版权负担；单款不引入任何游戏引擎，包体最小）。
- 状态：组件内状态机 + Pinia（如需跨工具共享会员态，复用方子现有计费 store）。
- 存储：IndexedDB（与方子现有 household-finance / local-knowledge-base 等工具一致），字段含 `bestScores`、`gameProgress`、`unlockedGames`。
- 计费：复用方子内置计费能力（Freemium：基础款免费，会员解锁完整游戏库/去广告/皮肤），接入现有计费 store 与付费弹窗组件。
- 音效：Web Audio API 程序化生成（可选、默认静音），避免音频素材授权问题。

### 盈利模式（可灵活扩展调整）

- 免费：全部基础玩法可玩（单局限制或基础款）。
- 会员：解锁完整游戏库、去广告位、主题皮肤、无限存档位。
- 后续可扩展：每日挑战、排行榜（纯本地/未来接入免费后端再议，本期不做）。

## 与 fangzi 现有代码的集成方式

- **新增目录**：`src/tools/games/`（遵循 fangzi 工具目录规范，含 manifest.json + 组件）。
- **复用**：现有工具框架的检索索引生成、路由自动注册、PWA 预缓存配置、计费 store（`src/core/` 下的公共模块）、样式体系（原生 CSS 变量）。
- **修改文件（最小化）**：原则上**不改**核心模块；如需要入口聚合（首页展示游戏列表子入口），仅按工具框架 manifest 声明；`package.json` 无需新增依赖（纯原生实现）。
- **衔接**：工具 manifest 中配置口语化关键词（小游戏、打发时间、摸鱼、2048、数独、益智、game 等），保证用户搜索直达。

## 软硬件/依赖选型

| 项 | 选型 | 商用授权状态 |
|---|---|---|
| 渲染 | 原生 Canvas 2D（无第三方库） | 不涉及 |
| 帧循环 | requestAnimationFrame（Web 标准） | 免费、无授权限制 |
| 音效 | Web Audio API 程序化生成 | 免费、无授权限制 |
| 存储 | IndexedDB（浏览器标准） | 免费 |
| 构建 | 复用 fangzi 现有 Vite/vite-plugin-pwa | MIT（项目既有） |
| 素材 | 程序化绘制/系统色板 | 不引入第三方素材，零版权风险 |

> 无新增依赖、无付费服务；所有选型均为标准 Web 能力，商用无限制。

## 开发方案

- 开发语言/框架：TypeScript + Vue 3 组件（与 fangzi 一致）。
- 环境：Node >= 20.19，`npm run new:tool -- games web "小游戏合集"` 生成骨架。
- 人员分工：独立开发者（本期单人多角色）。
- 里程碑：
  1. D1–D3：工具骨架 + GameShell + engine（loop/storage）；
  2. D4–D7：首批游戏 2048、翻牌配对；
  3. D8–D11：华容道、消消乐、数独；
  4. D12–D13：计费接入（会员解锁）、关键词与检索联调；
  5. D14–D15：构建/离线/回归/上线。

## 测试方案

- 单元测试（`test/*.test.ts`，复用 Node 内置 test runner + tsx）：游戏逻辑纯函数（2048 合并、数独校验、分数计算）、storage 读写。
- 组件/交互测试：GameShell 分数/重开/难度切换；各游戏单局可完成（冒烟）。
- **存量回归（硬性）**：`npm test` 全量通过；`npm run build` 通过（含 postbuild 体积校验）；`npm run verify:tools` 确保现有首页示例提问仍全部搜得到对应工具；人工走查现有 19 个工具入口正常。
- 验收标准：新增工具可搜索直达、可收藏、离线可玩、进度可恢复、会员解锁生效、存量功能零回归。

## 实施部署方案

- 部署架构：代码推送到 GitCode（`gitcode.com/m0_45688211/fangzi`）→ EdgeOne Pages 自动构建发布（现有流程）。
- 上线步骤：合并代码 → 触发 EdgeOne 构建 → 校验 `dist/` 体积 < 25MiB → 发布。
- 运维监控：EdgeOne 控制台访问量/错误率；PWA 缓存版本更新走 Workbox 自动管理。
- 回滚预案：Git 回滚上一发布版本，EdgeOne 重新构建；游戏功能为增量目录，回滚不影响其他工具。

## 风险与反思

- **用户真的需要吗？** 三次来信佐证真实；轻娱乐是碎片时间的普遍需求。
- **加了会不会把 fangzi 搞复杂？** 走工具框架新增目录，不侵入核心；游戏列表为独立入口，可「不打扰」地存在。
- **真的能节省时间、资金吗？** 提供情感价值（放松/成就感）；Freemium 具备变现空间，但主要价值是留存与活跃，不应过度投入。
- **遗留问题/待确认**：① 付费点（解锁完整库 vs 去广告）需产品最终拍板；② 游戏数量迭代节奏（用户期望「不断开发」）；③ 是否做每日挑战等长效机制（后续迭代）。这些不影响本期可集成结论。
